\section{Switch OS}
This section turns to the software that runs on the switch itself. A defining property of the bare-metal switches introduced in Section~\ref{sec:basic-architecture} is that hardware and software are no longer sold as a single vertically integrated unit: using the ONIE bootloader, the operator can install any compatible Switch OS on any bare-metal switch, much as an operating system of choice is installed on a commodity server~\cite{onie, systemsapproach}.

The analogy to a server extends to the hardware itself. A Linux server always provides a general-purpose processor, with its registers, memory, and I/O, before any operating system is loaded onto it. A bare-metal switch is built the same way: it contains a conventional CPU on which the Switch OS runs, complemented by a switching chip that acts as a packet-forwarding accelerator~\cite{systemsapproach}. The relationship between the two is closely analogous to that between a CPU and a GPU. The CPU runs the operating system and general-purpose software, and offloads a narrow but performance-critical workload to specialized hardware, here the forwarding of packets at line rate. The role of the Switch OS is therefore to expose the forwarding chip to the controller above it, receiving rules from the controller and installing them into the chip's tables. Beyond this, it performs only platform management, such as monitoring ports, transceivers, fans, and power supplies.

\subsection{Switch OS architecture}
The Switch OS considered here, Stratum, is described as a \textit{thin} Switch OS~\cite{systemsapproach}. It acts as a thin wrapper around the switch hardware API, exposing an interface through which a centralized SDN controller interacts with the hardware. Unlike the operating system of a conventional vertically integrated switch, it does not run complex, legacy control-plane protocol stacks locally; that logic resides in the controller.

On its northbound side, Stratum exposes three interfaces, each implemented as a gRPC service\footnote{gRPC is an open-source Remote Procedure Call (RPC) framework developed by Google for communication between services in data-center networks. Services and their messages are defined using Protocol Buffers.}~\cite{systemsapproach}:
\begin{itemize}
    \item \textbf{P4Runtime}, which controls the forwarding behavior of the switch by populating the tables defined in the P4 program;
    \item \textbf{gNMI} (gRPC Network Management Interface), which sets and retrieves the configuration of the switch;
    \item \textbf{gNOI} (gRPC Network Operations Interface), which manages the operational state of the switch.
\end{itemize}

For all three services, Stratum acts as the gRPC server and the Network OS as the client. The Network OS issues remote procedure calls against these services, and Stratum carries out each request on the switch hardware.

By building on gRPC and Protocol Buffers, these interfaces inherit solutions to backward compatibility, security, data format, and reliable delivery, concerns that network protocols, OpenFlow included, have historically had to address individually~\cite{systemsapproach}.\footnote{Protocol Buffers define a language-neutral data format whose schema can evolve without breaking existing clients. gRPC secures each channel with TLS and runs over TCP, which provides reliable, ordered delivery, and uses HTTP/2 to multiplex concurrent streams over a single TCP connection.}

On its southbound side, Stratum relies on two vendor- and platform-specific components. The first is the Software Development Kit (SDK) supplied by the switch-chip vendor, which reads and writes the chip's specialized hardware and memory, analogous to a device driver in a conventional operating system. The second is the Open Network Linux Platform (ONLP) API, which provides access to the switch's peripherals, such as hardware counters, monitoring sensors, and status variables~\cite{systemsapproach}. The remaining internal components of Stratum sit between these two sides and are designed to be vendor-agnostic, so that the same northbound interfaces are presented regardless of the chip or platform beneath them.

\subsection{P4Runtime}\label{sec:p4runtime}
Section~\ref{sec:p4-sdn-stack} ended with two files, \texttt{bmv2.json} and the P4Info, and an open question: how does a controller program tables it never defined? P4Runtime is the answer. P4Runtime is a control-plane protocol, built on gRPC and Protocol Buffers, through which a controller manages at runtime the data-plane entities of a device whose pipeline is defined by a P4 program, such as its tables, counters, and meters~\cite{p4runtime}. Every P4Runtime write has the same simple shape: put an entry in table $X$ that matches value $Y$ and runs action $Z$. The protocol itself does not know what $X$, $Y$, or $Z$ mean; the P4Info tells the controller which tables, fields, and actions exist, and the controller picks the values. Because nothing about specific headers is built into the protocol, P4Runtime achieves protocol independence, just as P4 does. This is exactly what OpenFlow could not do (Section~\ref{sec:openflow-limitation}), since its messages list the header fields a switch is allowed to match.

Besides writing table entries, P4Runtime also supports~\cite{p4runtime}:
\begin{itemize}
    \item Reading and updating other P4 objects, such as counters, meters, and action profiles.
    \item Multiple controllers per switch, so a backup can take over if the primary fails.
    \item Packet I/O, letting the switch send packets up to the controller and the controller send packets out through the switch.
    \item Batching many writes into one request.
    \item Loading a new P4 pipeline onto a switch that is already running.
\end{itemize}

Fig.~\ref{fig:p4runtime-workflow} shows the overall workflow with P4Runtime. The P4 compiler turns the program into two outputs: a target-specific binary for the switch chip, and the P4Info, which is shared by both ends of the connection. The controller runs the P4Runtime client, the Switch OS runs the P4Runtime server, and the two communicate using the messages defined in \texttt{p4runtime.proto}. The figure shows backends for two hardware chips (Tomahawk and Tofino); in this project the BMv2 backend is used instead, and its target-specific output is \texttt{bmv2.json}. In practice, the workflow proceeds as follows:

\begin{figure}[H]
    \centering
    \includegraphics[width=1\linewidth]{graphics/p4runtime-workflow.png}
    \caption{The P4Runtime workflow. Adapted from \cite{systemsapproach}.}
    \label{fig:p4runtime-workflow}
\end{figure}

\begin{enumerate}
    \item The P4 program is compiled into \texttt{bmv2.json} and the P4Info, and both are given to the controller (ONOS in this project, see Section~\ref{sec:onos}).
    \item When the switch boots, the controller connects to it and is elected as the controller in charge. The controller is the P4Runtime client; the Switch OS is the server.
    \item The controller sends both files to the switch. The Switch OS loads \texttt{bmv2.json} into the forwarding chip, and keeps the P4Info so it understands the table and action IDs in later requests.
    \item The controller starts writing table entries, and the switch begins forwarding traffic.
\end{enumerate}

To make this concrete, Listing~\ref{lst:l2-exact} shows the table \texttt{main.p4} uses for unicast bridging, and Listing~\ref{lst:l2-exact-p4info} shows what the compiler wrote about it in \texttt{p4info.txt}.

\begin{lstlisting}[caption={The \texttt{l2\_exact\_table} in \texttt{main.p4}.},label={lst:l2-exact}]
action set_egress_port(port_num_t port_num) {
    standard_metadata.egress_spec = port_num;
}

table l2_exact_table {
    key = {
        hdr.ethernet.dst_addr: exact;
    }
    actions = {
        set_egress_port;
        @defaultonly drop;
    }
    const default_action = drop;
}
\end{lstlisting}

\begin{lstlisting}[language={},caption={The P4Info entries for \texttt{l2\_exact\_table} and its actions.},label={lst:l2-exact-p4info}]
tables {
  preamble {
    id: 33605373
    name: "IngressPipeImpl.l2_exact_table"
    alias: "l2_exact_table"
  }
  match_fields {
    id: 1
    name: "hdr.ethernet.dst_addr"
    bitwidth: 48
    match_type: EXACT
  }
  action_refs { id: 16812802 }
  action_refs {
    id: 16796182
    annotations: "@defaultonly"
    scope: DEFAULT_ONLY
  }
  const_default_action_id: 16796182
  size: 1024
}
actions {
  preamble {
    id: 16812802
    name: "IngressPipeImpl.set_egress_port"
    alias: "set_egress_port"
  }
  params {
    id: 1
    name: "port_num"
    bitwidth: 9
  }
}
actions {
  preamble {
    id: 16796182
    name: "IngressPipeImpl.drop"
    alias: "drop"
  }
}
\end{lstlisting}

Notice that the P4Info says nothing about how the table works; it only gives the controller names, IDs, and sizes. The table is ID 33605373, its key is a 48-bit exact match on the destination MAC address, and the action \texttt{set\_egress\_port} is ID 16812802 with one 9-bit parameter. The \texttt{drop} action is marked \texttt{DEFAULT\_ONLY}, so the controller cannot use it in a normal entry. This is all the controller needs to write entries into the table.

To install an entry, the controller uses the P4Info to build a P4Runtime message. Each table, field, and action is identified by its ID, and each value is encoded in bytes according to the bit width given in the P4Info: 48 bits for the MAC address and 9 bits for the port. The message is sent to the switch with the \texttt{Write} RPC. For a host with MAC address \texttt{00:00:00:00:00:1a} attached to port 3, the request looks like Listing~\ref{lst:write-request}. Further details on how the controller builds this request in this project are given as an example in Section~\ref{sec:onos-write}.

\begin{lstlisting}[language={},caption={The resulting P4Runtime \texttt{Write} request (simplified).},label={lst:write-request}]
updates {
  type: INSERT
  entity {
    table_entry {
      table_id: 33605373
      match {
        field_id: 1
        exact { value: "\x00\x00\x00\x00\x00\x1a" }
      }
      action {
        action {
          action_id: 16812802
          params {
            param_id: 1
            value: "\x03"
          }
        }
      }
    }
  }
}
\end{lstlisting}

The \texttt{type} field tells the switch what to do with the entry: \texttt{INSERT} adds it, \texttt{MODIFY} changes its action, for example if the host moves to another port, and \texttt{DELETE} removes it. On the switch side, the Switch OS uses its copy of the P4Info to resolve the IDs and installs the entry into the forwarding chip. From then on, frames addressed to that host leave through port 3 without involving the controller. The controller can also call the \texttt{Read} RPC to fetch the table's current entries, which it uses to check that the switch still holds the rules it expects.

\subsection{YANG and OpenConfig}\label{sec:yang-openconfig}
YANG and OpenConfig are the groundwork on which the gNMI and gNOI interfaces of Section~\ref{sec:gnmi-gnoi} are built. To see why they are needed, it is useful to first consider how device state has traditionally been described. Historically, network devices exposed their state through a Management Information Base (MIB): a standardized dictionary of device variables, such as interface status, health indicators, and traffic counters, defined uniformly across devices and therefore independent of any particular vendor~\cite{systemsapproach}. Used together with the Simple Network Management Protocol (SNMP), the MIB gave operators read access to this state for monitoring purposes. The shift to SDN, however, requires write access as well, since a controller must not only observe a device but also configure it. Meeting this requirement meant revisiting how the device data model itself is defined~\cite{systemsapproach}.

YANG is the modeling language that emerged to fill this role. A YANG model defines each device variable together with a human-readable description of its meaning, while remaining precise enough to be read and written programmatically. In this respect YANG plays a role similar to XML Schema (XSD) or JSON Schema: it defines the structure of the data. Unlike those schema languages, however, YANG is not tied to a single encoding. XSD describes only XML documents and JSON Schema only JSON documents, whereas data defined by a YANG model can be encoded as XML, JSON, or Protocol Buffers~\cite{systemsapproach}.

OpenConfig is an industry-wide standardization effort, driven by network operators that are driving to a convergence, vendor-neutral, programmable network model~\cite{openconfig}. The effort has two parts. The first is a set of data models, written in YANG, that describe the configuration and operational state of common device features, such as interfaces, routing protocols, and platform components, in the same way on every vendor's equipment. The second is a family of modern RPC-based interfaces built on gRPC: gNMI for reading and writing configuration and state, gNOI for performing operational actions on the device, gRIBI (gRPC Routing Information Base Interface) for programming routing entries, and gNSI (gRPC Network Security Interface) for managing the device's security policies, such as certificates and access control. These interfaces are intended as alternatives to traditional management protocols such as SNMP and NETCONF\footnote{NETCONF is an IETF protocol for installing and retrieving device configuration, encoded in XML and typically carried over SSH. YANG was originally designed as the modeling language for NETCONF.}.

Listing~\ref{lst:oc-interfaces} shows an example of an OpenConfig model, \texttt{openconfig-interfaces}, which describes the network interfaces of a device. The model is shown in the YANG tree diagram notation, in which each line is a node of the data tree: \texttt{rw} marks configuration that a client can read and write, \texttt{ro} marks operational state that is read-only, \texttt{*} marks a list whose entries are identified by the key in brackets, and \texttt{?} marks an optional node. The model defines a list of interfaces keyed by name, and each interface keeps its configuration (\texttt{config}) separate from its operational state (\texttt{state}), a convention followed throughout the OpenConfig models.

\begin{lstlisting}[language={},caption={The base OpenConfig model for network interfaces (abridged). Adapted from \cite{systemsapproach}.},label={lst:oc-interfaces}]
module: openconfig-interfaces
  +--rw interfaces
     +--rw interface* [name]
        +--rw name
        +--rw config
        |  ...
        +--ro state
        |  ...
        +--rw hold-time
        |  ...
        +--rw subinterfaces
           ...
\end{lstlisting}

The base model describes only the properties that are common to every kind of interface. Properties specific to a particular kind of interface are added by separate modules through \textit{augmentation}, which attaches new nodes to an existing model without modifying it. Listing~\ref{lst:oc-ethernet} shows the \texttt{openconfig-if-ethernet} module, which augments each interface with an \texttt{ethernet} container. This container holds Ethernet-specific configuration, such as the MAC address, port speed, and duplex mode, together with the corresponding state, such as the hardware MAC address and the interface counters.

\begin{lstlisting}[language={},caption={The Ethernet augmentation of the OpenConfig interfaces model (abridged). Adapted from \cite{systemsapproach}.},label={lst:oc-ethernet}]
module: openconfig-if-ethernet
  augment /oc-if:interfaces/oc-if:interface:
    +--rw ethernet
       +--rw config
       |  +--rw mac-address?
       |  +--rw auto-negotiate?
       |  +--rw duplex-mode?
       |  +--rw port-speed?
       |  +--rw enable-flow-control?
       +--ro state
          +--ro mac-address?
          +--ro auto-negotiate?
          +--ro duplex-mode?
          +--ro port-speed?
          +--ro enable-flow-control?
          +--ro hw-mac-address?
          +--ro counters
             ...
\end{lstlisting}

Technically, gNMI can operate on any YANG model, and in contrast, YANG is also not tied to either gRPC or gNMI; in Stratum, however, the two are used together, with gNMI exposing the switch's configuration and state through the OpenConfig models. Both interfaces are described next.

\subsection{gNMI and gNOI}\label{sec:gnmi-gnoi}
gNMI defines a small set of RPCs through which a client reads and writes the data tree described by the device's YANG models~\cite{gnmi}. Listing~\ref{lst:gnmi-service} shows the four RPCs that gNMI defines:
\begin{itemize}
    \item \texttt{Capabilities} returns the capabilities of the target: the YANG models it implements, the encodings it accepts, and the gNMI version it supports;
    \item \texttt{Get} retrieves a snapshot of data from the target;
    \item \texttt{Set} modifies data on the target;
    \item \texttt{Subscribe} opens a stream over which the target sends updates for the data that the client has subscribed to.
\end{itemize}

\begin{lstlisting}[language={},caption={The RPCs defined by the gNMI service.},label={lst:gnmi-service}]
service gNMI {
    rpc Capabilities(CapabilityRequest)
        returns (CapabilityResponse);
    rpc Get(GetRequest) returns (GetResponse);
    rpc Set(SetRequest) returns (SetResponse);
    rpc Subscribe(stream SubscribeRequest)
        returns (stream SubscribeResponse);
}
\end{lstlisting}

gNOI complements gNMI by covering operations that are not naturally expressed as reading or writing a value in the data tree, such as rebooting the switch, testing reachability, installing certificates, or transferring files~\cite{gnoi}. Unlike gNMI, gNOI does not rely on YANG models: each operation is defined directly as an RPC in Protocol Buffers, and related operations are grouped into separate services, such as \texttt{System}, \texttt{Cert}, and \texttt{File}. Listing~\ref{lst:gnoi-system} shows part of the \texttt{System} service.

\begin{lstlisting}[language={},caption={Part of the gNOI \texttt{System} service.},label={lst:gnoi-system}]
service System {
    rpc Ping(PingRequest)
        returns (stream PingResponse) {}
    rpc Traceroute(TracerouteRequest)
        returns (stream TracerouteResponse) {}
    rpc Reboot(RebootRequest)
        returns (RebootResponse) {}
    // ...
}
\end{lstlisting}
