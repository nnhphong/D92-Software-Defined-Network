% TODO: put a section on bare-metal switches hardware %
Before turning to what P4 is and how the language itself is structured, it is worth establishing why a new data-plane programming model was needed at all. OpenFlow was built to reuse capability that switch vendors already had on-chip: McKeown et al.\ note that ``we exploit the fact that most modern Ethernet switches and routers contain flow-tables (typically built from TCAMs)'' used internally to implement functions such as firewalling, NAT, QoS, and statistics collection, and that OpenFlow simply exposes ``this common set of functions'' through a standard interface~\cite{mckeown2008openflow}. This was a deliberate compromise: rather than requiring new switch hardware, the design goal was a datapath ``amenable to high-performance and low-cost implementations,'' which meant ``forgoing the ability to specify arbitrary handling of each packet and seeking a more limited, but still useful, range of actions''~\cite{mckeown2008openflow}. In its original 2008 form this amounted to a single flow table matched against about a dozen header fields such as MAC address, IP address, protocol, and TCP/UDP ports~\cite{bosshart2014p4}.

\subsection{The fundamental limitation of OpenFlow}
That original dozen-field flow table did not remain fixed for long. The formal OpenFlow 1.0 specification followed the 2008 proposal in December 2009, and each successive revision of the OpenFlow 1.x line extended the matchable field set to accommodate new headers, so that the number of supported fields rose from 12 to 41 by 2013~\cite{bosshart2014p4}. Yet as data-center networking continued to evolve, operators kept demanding support for still newer encapsulation headers (e.g., VXLAN, NVGRE); rather than continuing to extend OpenFlow 1.x indefinitely, researchers proposed a strawman ``OpenFlow 2.0'' interface instead~\cite{bosshart2014p4}.

The push toward an OpenFlow 2.0 interface reflected two distinct pressures on any successor design: the need to keep pace with the rapid rate of change in networking requirements, and the need for a design that remained viable over the long term. The immediate problem was one of deployment speed. At the time, bare-metal switches still relied on a fixed-function pipeline hardcoded into the switch firmware to match packets, so supporting a new protocol required two slow steps in sequence. First, the protocol itself had to be agreed upon. Second, once agreed upon, the switch firmware itself had to be updated, since the firmware had no built-in intelligence to parse a raw packet format it had never been told about, and changing the firmware took still more time. Consequently, simply adding a new protocol to the specification was not enough on its own: it could still take vendors years to release a new switch model incorporating it, and for that hardware to then be adopted into the already-deployed network. The implication was that future switches should be able to define custom headers themselves, and that controller applications should likewise be able to understand these custom headers.

\subsection{Existing efforts for programmable pipelines}
Programmable forwarding pipelines existed well before P4, in several forms, each trading away something essential. Software switches and modular frameworks such as Click~\cite{kohler2000click} offered complete flexibility, but executed on general-purpose CPUs and therefore operated far below the line rates expected of a switch ASIC; Click was also not designed for the controller-switch split that SDN assumes, and so provided no notion of match-action tables populated at runtime by a controller~\cite{bosshart2014p4}. At the other extreme, network processors, FPGAs, and---by 2013---reconfigurable match-action ASICs such as RMT~\cite{bosshart2013rmt} had demonstrated that this flexibility could in fact be achieved at terabit speeds. The obstacle there was not capability but usability: each chip exposed its own proprietary low-level interface, which Bosshart et al.\ compare to microcode programming, so a forwarding behavior written for one target could not be carried to another~\cite{bosshart2014p4}. The gap P4 was created to fill is therefore a linguistic one rather than a hardware one: it provides a high-level, protocol-agnostic language that a compiler can translate into the configuration each target requires, including the line-rate programmable ASIC pipelines these chips had already made possible~\cite{bosshart2014p4}.

\subsection{Flexible resource allocation}
A further advantage of a programmable data plane over a fixed-function pipeline is in how on-chip memory is distributed among tables. In a fixed-function switch, both the set of supported protocols and the memory reserved for each table are fixed in silicon at design time, regardless of how a particular network actually uses them. A programmable pipeline instead treats its memory as a shared pool that the program can partition according to need, allowing table sizes to be matched to the deployment~\cite{bosshart2013rmt}. Fig.~\ref{fig:dynamic-resource-allocation} illustrates this with a pipeline of four equal memory blocks. A fixed-function design dedicates one block each to the Ethernet, IPv4, IPv6, and ACL tables. If the network instead carries predominantly IPv4 traffic, a P4 program can declare an IPv4 table twice as large, occupying two blocks, while the IPv6 and ACL tables share the remaining one.

\subsection{Forwarding pipeline}
At the architecture level, researchers introduced PISA (Protocol Independent Switching Architecture) as the pipeline design that gives P4 its reconfigurability~\cite{systemsapproach}. As shown in Fig.~\ref{fig:pisa-pipeline}, a PISA pipeline is built from three components---a programmable parser, a programmable multi-stage match-action pipeline, and a programmable deparser---each configured by the P4 program itself rather than hardcoded into switch firmware. This generic, configurable structure is what lets the same abstract model describe packet processing across otherwise substantially different forwarding devices---Ethernet switches, load-balancers, and routers---and across different underlying technologies, whether a fixed-function switch ASIC, an NPU, a reconfigurable switch, a software switch, or an FPGA~\cite{bosshart2014p4}.

\begin{figure}[H]
    \centering
    \includegraphics[width=1\linewidth]{graphics/forwarding-pipeline.png}
    \caption{Abstract forwarding pipeline that model how most data plane devices are forwarding packet. Adapted from \cite{systemsapproach}.}
    \label{fig:pisa-pipeline}
\end{figure}

The parser forms the first stage of the pipeline and extracts header fields from an incoming packet by walking a program-defined parse graph: it sequentially extracts each header and copies its values into the memory defined by that header's structure (e.g., the IPv4 header). Once extracted, these fields are passed to the match-action pipeline, where the design's protocol independence is most apparent. Each stage of the pipeline pairs a block of memory---combining SRAM and TCAM~\cite{systemsapproach}---with an ALU. This memory is not preloaded by the switch vendor to recognize a fixed set of headers; that is, it does not inherently support IPv4 but not IPv6, or TCP but not UDP. It instead behaves as a generic bank of lookup-table entries that the P4 program itself populates at configuration time, using the match keys that a given header requires. The lookup is performed by the memory: the TCAM supports wildcard matching of the arriving packet's fields against the programmed entries, while exact matches are served from SRAM at lower cost~\cite{systemsapproach}. Only after a match is found does the ALU execute the action associated with the matched entry. Because each stage can be pipelined---one stage processing one packet while the next stage concurrently processes another---this reprogrammable design still sustains line-rate throughput~\cite{systemsapproach}. Finally, the deparser reassembles the modified header fields into a single serialized packet before it leaves the pipeline, following the header layout defined by the program.

\subsection{Abstracting the pipeline}
The pipeline described so far is a generic model, reduced to three components and abstracted away from any particular chip design. Production ASICs are considerably more elaborate and complex than this, and their pipelines differ from one vendor to the next, which raises the question of how a single program, or a single controller, can be written against such a variety of physical pipelines. The response is to interpose a single \textit{logical pipeline}: an abstract model of the forwarding pipeline that programs and controllers are written against, and which a compiler, provided by the vendor themselves, then maps onto the physical pipeline of a given chip. With such a model in place, controllers become pipeline-agnostic~\cite{systemsapproach}. Fig.~\ref{fig:abstract-pipeline} illustrates this arrangement: the controller addresses a logical pipeline, and the P4 compiler maps that logical pipeline onto the differing physical pipelines of each ASIC beneath it.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=1\linewidth]{graphics/abstract-pipeline.png}
    \caption{A logical pipeline mapped by the P4 compiler onto the physical pipelines of two different ASICs. Adapted from \cite{systemsapproach}.}
    \label{fig:abstract-pipeline}
\end{figure}

The Portable Switch Architecture (PSA) is the standardization of this idea, developed by the P4 Consortium as a community effort~\cite{systemsapproach}. It is intended to give P4 developers an abstract target machine, analogous to a Java Virtual Machine, and with it a write-once-run-anywhere programming model~\cite{systemsapproach}. The industry, however, has not followed. Vendors do not provide the compiler backend that would map PSA onto their respective ASICs, which is precisely what the model depends on, and PSA therefore remains a mostly ``on paper'' artifact~\cite{systemsapproach}. The incentives run the other way: vendors face their own version of the multi-ASIC problem as they release new chips over time, and defining an architecture of their own allows them to expose the distinctive capabilities of their silicon without being constrained by a standardization process~\cite{systemsapproach}. What P4 developers write against in practice is therefore either V1Model, the simpler model illustrated in Fig.~\ref{fig:v1model-pipeline}, or a vendor-specific architecture such as the Tofino Native Architecture (TNA), defined by Barefoot for its family of programmable switching chips~\cite{systemsapproach}. In the latter case both the architecture and its backend compiler are proprietary, and the P4 program must conform to them. The portability objective is therefore not achieved: vendors retain the freedom to define their own pipelines, and a developer must write P4 against the architecture of the target in use. The resulting position nonetheless represents a significant advance on fixed-function forwarding. The pipeline is no longer determined in silicon by the vendor but is instead exposed to the developer, and it is this programmability, rather than portability across targets~\cite{systemsapproach}.

\subsection{Example of a P4 program}
The preceding subsections described the forwarding pipeline in the abstract; this subsection grounds that description in a concrete program. The example used throughout is \texttt{main.p4}, the P4 program written for this project, which is compiled for and executed on BMv2, the reference P4 software switch~\cite{bmv2}. The program declares a range of header formats---Ethernet, IPv4, IPv6, TCP, UDP, ICMP, ICMPv6, and NDP---together with Segment Routing over IPv6 (SRv6) headers and a pair of CPU headers that carry packet-in and packet-out messages between the pipeline and the controller. The subsections that follow examine the program in the order a packet encounters it: the architecture it must conform to, the header formats it defines, the parser that extracts them, the tables that match on the extracted fields, and the actions those tables invoke.

\subsubsection{The V1Switch pipeline}
BMv2 executes programs written for the \texttt{v1model} architecture~\cite{bmv2}, whose \texttt{V1Switch} package fixes both the blocks a program must provide and the order in which they run: a parser, a checksum-verification block, an ingress pipeline, an egress pipeline, a checksum-computation block, and a deparser (Listing~\ref{lst:v1switch}). A program cannot add, reorder, or omit a stage; a block it does not need must still be supplied with an empty body. These six are only the programmable stages. As shown in Fig.~\ref{fig:v1model-pipeline}, the architecture also places a fixed-function traffic manager between the ingress and egress pipelines, which queues, replicates, and schedules packets~\cite{systemsapproach}; it is not expressed in P4 and is directed only indirectly, through the metadata written during ingress.



\begin{lstlisting}[caption={Instantiating the \texttt{V1Switch} pipeline in \texttt{main.p4}.},label={lst:v1switch}]
V1Switch(
    ParserImpl(),
    VerifyChecksumImpl(),
    IngressPipeImpl(),
    EgressPipeImpl(),
    ComputeChecksumImpl(),
    DeparserImpl()
) main;
\end{lstlisting}

\subsubsection{Header and metadata formats}
P4 uses a C-like syntax for its type declarations, which makes this part of the program largely self-explanatory. A header is declared as an ordered sequence of named fields with explicit bit widths, and the program is free to define any header it requires; Listing~\ref{lst:headers} shows the Ethernet and IPv4 definitions. Widths may be given names of their own through \texttt{typedef}---for example \texttt{typedef bit<48> mac\_addr\_t}, naming the 48 bits that hold a MAC address. Values the program matches against are declared as named constants, such as \texttt{IP\_PROTO\_ICMP = 1} and \texttt{IP\_PROTO\_TCP = 6}, whose values are the protocol numbers assigned in RFC~790~\cite{rfc790}. Alongside the headers, the program declares a metadata structure carrying the per-packet state the pipeline needs but that is not necessary to appear on the wire.

Not every header declared in this way corresponds to a protocol carried on the network. Listing~\ref{lst:headers} also defines \texttt{cpu\_in\_header\_t}, which is prepended to packets sent to the controller over the CPU port and records the port on which the packet originally arrived. The \texttt{@controller\_header("packet\_in")} annotation identifies it as a control-plane header, from which the P4Runtime server populates the metadata fields of the corresponding packet-in message. A second header, \texttt{cpu\_out\_header\_t}, serves the opposite direction, informing the pipeline of the port on which a packet received from the controller is to be transmitted. The declaration mechanism is therefore the same whether a header describes a standard protocol or a format defined solely for exchange between the pipeline and its control plane.

\begin{lstlisting}[caption={Header definitions in \texttt{main.p4}.},label={lst:headers}]
#include <core.p4>
#include <v1model.p4>

typedef bit<9>   port_num_t;
typedef bit<48>  mac_addr_t;
typedef bit<32>  ipv4_addr_t;

const bit<16> ETHERTYPE_IPV4 = 0x0800;
const bit<8> IP_PROTO_ICMP   = 1;
const bit<8> IP_PROTO_TCP    = 6;

header ethernet_t {
    mac_addr_t  dst_addr;
    mac_addr_t  src_addr;
    bit<16>     ether_type;
}

header ipv4_t {
    bit<4>   version;
    bit<4>   ihl;
    bit<6>   dscp;
    bit<2>   ecn;
    bit<16>  total_len;
    bit<16>  identification;
    bit<3>   flags;
    bit<13>  frag_offset;
    bit<8>   ttl;
    bit<8>   protocol;
    bit<16>  hdr_checksum;
    bit<32>  src_addr;
    bit<32>  dst_addr;
}

@controller_header("packet_in")
header cpu_in_header_t {
    port_num_t  ingress_port;
    bit<7>      _pad;
}
\end{lstlisting}

\subsubsection{Packet parser}
The parser is expressed as a finite state machine. Each state is introduced by the \texttt{state} keyword, and the transition out of that state is declared inside the state body itself. 

\begin{lstlisting}[caption={Parser state machine in \texttt{main.p4}.},label={lst:parser}]
parser ParserImpl (packet_in packet,
            out parsed_headers_t hdr,
            inout local_metadata_t l_metadata,
            inout standard_metadata_t metadata) {
state start {
    transition select(metadata.ingress_port) {
        CPU_PORT: parse_packet_out;
        default: parse_ethernet;
    }
}

state parse_packet_out {
    packet.extract(hdr.cpu_out);
    transition parse_ethernet;
}

state parse_ethernet {
    packet.extract(hdr.ethernet);
    transition select(hdr.ethernet.ether_type){
        ETHERTYPE_IPV4: parse_ipv4;
        ETHERTYPE_IPV6: parse_ipv6;
        default: accept;
    }
}
\end{lstlisting}

Execution begins in the built-in \texttt{start} state; each subsequent state extracts one header from the packet into the header structure declared earlier, then transitions to the state responsible for interpreting the bytes that follow. The machine terminates in one of two built-in states: \texttt{accept}, marking the end of parsing and handing the extracted headers to the pipeline, or \texttt{reject}, marking a parsing failure~\cite{p4spec}.

\subsubsection{Ingress processing}
Ingress is the stage in which forwarding decisions are made. It is expressed as a set of match-action tables together with an \texttt{apply} block that sequences them. A table declares three things: the \texttt{key} it matches on, paired with a match kind such as \texttt{exact} or \texttt{ternary}; the set of \texttt{actions} that an entry may invoke; and the \texttt{default\_action} taken when no entry matches. The table itself holds no entries in the program; these are installed at runtime by the controller, which is what allows forwarding policy to change without recompiling the pipeline. Listing~\ref{lst:ingress} shows the L2 forwarding table and the action it invokes.

\begin{lstlisting}[caption={An ingress table, its action, and the control flow that applies it.},label={lst:ingress}]
action set_egress_port(port_num_t port_num) {
    standard_metadata.egress_spec = port_num;
}

table l2_exact_table {
    key = {
        hdr.ethernet.dst_addr: exact;
    }
    actions = {
        set_egress_port;
        @defaultonly drop;
    }
    const default_action = drop;
}

apply {
    if (!l2_exact_table.apply().hit) {
        l2_ternary_table.apply();
    }
    acl_table.apply();
}
\end{lstlisting}

Two properties of this arrangement are worth noting. First, an action may take parameters, such as \texttt{port\_num} above, whose values are supplied by the matched entry at runtime rather than fixed in the program. Second, applying a table returns a result whose \texttt{hit} field can be tested, so the \texttt{apply} block expresses ordinary imperative control flow over the tables: here the exact-match table is consulted first, and the ternary table only if no entry matched. Forwarding is ultimately determined by writing \texttt{standard\_metadata.egress\_spec}, which the traffic manager reads once ingress completes.

\subsubsection{Egress processing}
Egress runs after the traffic manager, and therefore executes once per copy of the packet, at a point where the output port has already been fixed and is available read-only as \texttt{standard\_metadata.egress\_port}. Its role is consequently narrower than that of ingress: it applies adjustments that depend on the specific copy or on its destination port, as shown in Listing~\ref{lst:egress}.

\begin{lstlisting}[caption={Egress processing in \texttt{main.p4}.},label={lst:egress}]
apply {
    if (standard_metadata.egress_port == CPU_PORT) {
        hdr.cpu_in.setValid();
        hdr.cpu_in.ingress_port = standard_metadata.ingress_port;
    }

    if (local_metadata.is_multicast == true &&
          standard_metadata.ingress_port ==
          standard_metadata.egress_port) {
        mark_to_drop(standard_metadata);
    }
}
\end{lstlisting}

The first condition handles packets destined for the controller: the \texttt{cpu\_in} header is marked valid and stamped with the port on which the packet originally arrived, so that the controller receiving the packet-in message can recover that context. The second implements split horizon for multicast. Because replication has already occurred, one of the copies may be addressed to the port the packet arrived on; that copy is dropped, which prevents a broadcast NDP solicitation from being reflected back to its sender. Neither decision can be made during ingress, since neither the copy nor its egress port exists at that point.

\subsubsection{Deparser}
The deparser reassembles the outgoing packet. Its headers are passed as \texttt{in} parameters and are therefore read-only, and the only operation permitted is \texttt{emit}, so no further modification is possible at this stage~\cite{p4spec}. The program specifies a single, static emission order, given in Listing~\ref{lst:deparser}.

\begin{lstlisting}[caption={The deparser in \texttt{main.p4}.},label={lst:deparser}]
control DeparserImpl(packet_out packet, in parsed_headers_t hdr) {
    apply {
        packet.emit(hdr.cpu_in);
        packet.emit(hdr.ethernet);
        packet.emit(hdr.ipv4);
        packet.emit(hdr.ipv6);
        packet.emit(hdr.srv6h);
        packet.emit(hdr.srv6_list);
        packet.emit(hdr.tcp);
        packet.emit(hdr.udp);
        packet.emit(hdr.icmp);
        packet.emit(hdr.icmpv6);
        packet.emit(hdr.ndp);
    }
}
\end{lstlisting}

Although the order is fixed, the emitted packet is not. An \texttt{emit} on a header that is not valid has no effect, so only those headers that the parser extracted, or that the pipeline subsequently marked valid, appear on the wire. A single sequence therefore serializes packets of different shapes correctly: an IPv4 packet emits \texttt{ipv4} and skips \texttt{ipv6}, an IPv6 packet does the reverse, and a packet sent to the controller additionally carries the \texttt{cpu\_in} header that egress marked valid.

\subsection{P4 within the wider SDN stack}
The preceding subsections treated the P4 program in isolation. In practice it is one component among several, and compilation is the point at which it is joined to the rest of the stack. The vendor supplies both the architecture and the backend compiler for its chips; the developer writes a program conforming to that architecture; and the compiler translates the program into a form the target can load. For the example used here, the program is compiled by \texttt{p4c-bm2-ss} compiler provided by BMv2 switch community against the \texttt{v1model} architecture, which produces two distinct outputs.

The first, \texttt{bmv2.json}, is the target-specific configuration the software switch loads to realize the pipeline. The second, \texttt{p4info.txt}, is a Protocol Buffers description of the interface through which the control plane addresses that pipeline: the tables it contains, the match fields and match types each is keyed on, the actions each may invoke and their parameters, together with the numeric identifiers by which a controller refers to them over P4Runtime. The former determines how packets are processed; the latter determines how that processing is populated, and it answers a question left open earlier, namely how a controller configures a pipeline it did not define. No part of the forwarding logic is communicated to the controller; the P4Info contract is. Both endpoints hold that contract, since the P4Runtime pipeline configuration message carries the P4Info alongside the target-specific configuration: the switch agent needs the same mapping to resolve the requests it receives.
